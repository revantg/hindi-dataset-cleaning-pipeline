Fertility is our real data budget

In Session 2 we saw that a tokenizer cuts text into tokens, and the consequence for collection is that a high-fertility tokenizer, meaning one that produces more tokens per word, burns more tokens for the same meaning so that a fixed token budget ends up covering fewer documents. Because the same sentence costs far more tokens in Indic scripts under a generic English-centric tokenizer, the Indic corpus has to be sized in information, not tokens.

The lesson for V5 sourcing is that we should not size the Indic corpus in tokens, because a token of Telugu carries far less text than a token of English under a generic tokenizer. We want instead to size it in information and to choose a tokenizer that does not tax the languages we most want to protect. tokens ≠ information
